# Easy Wiki Skill

从零搭建 LLM 知识库的引导 Skill。说一句"我想搭建知识库"，它会先确认这个库是给谁用的、什么算合格的内容、什么不该进库，然后生成一套能被 AI 长期维护的知识库。

---

## 这个 Skill 解决什么问题

在实际搭建个人和企业知识库之后，我们发现了这些普遍痛点：

- 文件越收越多，用的时候还是找不到
- 写下来的只有结论，说不清为什么这么定
- 同一件事有三份文档，不知道哪份有效
- 建完三个月没人管，旧内容开始误导人

**问题不在工具，在于从哪儿出发。**

知识管理是**管理学与工程学的结合**：管理学定目标、定怎么拆，工程学把拆出来的东西做成能执行的形式。过去的知识库大多只做到了后一半：

| | 出发点 | 做法 | 结果 |
|---|---|---|---|
| 旧做法 | 我手上有什么知识 | 从存量**归纳**：先盘点，再琢磨怎么归类放好 | 一堆整齐但没用的文件夹 |
| 这个 Skill | 要解决什么问题 | 从目标**演绎**：先讲清问题和受众，再倒推需要哪些知识、什么结构能让它在需要时被找到 | 一个能找到、能用的库 |

所以第一步**不是建目录，是访谈**：把场景和目标问清楚，拿你真实的材料当种子跑一遍，从材料里拆出"什么内容归到哪、什么算合格、什么该拒绝"的规则。Karpathy 的 [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f#file-llm-wiki-md) 讲的是同一件事：**人负责定目标和规则，agent 负责整理和维护。**

规则写进 `AGENTS.md` 之后，循环就很简单：你投料、看结果、发现不对就改规则。**库靠规则运转，不靠你的记忆。**

具体是四件事：

1. **判断场景**：这个库的主角是"我"、"一位专家"、"老板"、"一件在办的事"，还是"一个部门"。五者的合格标准不同，套同一套目录会退化。
2. **访谈**：把说不清的判断问成写得下来的规则，并用你给的真实材料跑一遍。
3. **生成 `AGENTS.md`**：把归属规则、回答纪律、拒绝清单写进文件，以后每次投料都按这套规则处理。
4. **三工作流 + Lint**：Ingest / Query / Lint 让库在三个月后还在更新。

访谈只是第 2 步。它负责拿到内容，不负责让库活下来。

## 快速开始

### 1. 安装

```bash
npx skills add https://github.com/ElanneWang/yike-easywiki-skill.git
```

没有 npx 环境时，把整个目录复制到 skills 目录即可：全局用 `~/.claude/skills/`（或对应工具的 skills 目录），只给当前项目用就放到项目的 `.agents/skills/` 下。复制后确认 `SKILL.md` 在目录第一层，不要多套一层文件夹。

### 2. 触发

在你的 AI 编码工具里打开任意目录（新建一个空目录最好），说：

> 我想搭建一个知识库

### 3. 跟着访谈走

Skill 会先问 4-5 个问题判断场景，再针对场景深入访谈 3-5 轮。整个过程通常 20-40 分钟。

访谈中会做两件事：

- **要真实材料**：不是让你描述需求，是让你给一份真实的会议转写、文章、或文档
- **当场跑一遍**：用你给的材料走完整摄入流程，让你看见机制怎么运转，而不只是听描述

访谈结束后你会得到一个可以直接用 git 管理的知识库目录，里面包含 `AGENTS.md`——这份文件决定了你的 AI 之后怎么维护这个库。

## 六种场景

场景判断的问题是：**这个知识库的主角是谁，或者是什么？**

| 场景 | 知识的主角 | 适用人群 | 解决什么 |
|------|-----------|---------|---------|
| 一、个人产能型 | 我 | 研究者、创业者、投资人、创作者 | 消费的外部信息沉淀成自己的判断 |
| 二、业务专家型 | 我（一位专家） | 产品经理、研发、销售、专业顾问、交付负责人 | 我的判断变成团队和上下游能直接用的标准 |
| 三、决策分身型 | 老板 | 创始人/一把手，及其助理、顾问 | 老板的判断体系变成组织资产 |
| 四、项目协作型 | 一件在办的事 | 售前、咨询、知识服务、定制交付 | 项目过程可追溯，状态不依赖个人记忆 |
| 五、部门共建型 | 一个部门 | 部门负责人、制度/流程维护人、团队 leader | 多人的判断合成统一口径，制度可追溯版本 |
| 六、开放定义型 | 你自己定义 | 前五类都不像的个人用途 | 按你自己的理解建库，只保留三条底线 |

> 编号在 v0.3 调整过：原「场景五 开放定义型」现在是场景六，腾出的场景五给部门知识库。如果你按旧编号记过笔记，只需把"开放"的编号往后移一位。

### 场景一：个人产能型

给知识库自己用：看的文章、听的播客、做的实验、想到的点子，最后合成自己的判断和产出。

```
wiki/
├── concepts/      # 概念页：一个概念一页，标注来源和我的理解
├── cases/         # 案例页：发生了什么、为什么重要
├── sources/       # 信源摘要：每篇文章/播客的提炼
├── thoughts/      # 个人思考：不成熟的判断也留存
├── entities/      # 实体：反复出现的人、公司、产品
├── synthesis/     # 综合分析：多个信源交叉后的结论
└── outputs/       # 产出文档
```

### 场景二：业务专家型

给一位业务专家的协作者用：团队内部的规范与资料解读，上下游的审核与交付标准——把专业判断写成别人能直接执行的规则、检查清单、术语表。

关键区别是**单点权威**：一个人定，别人执行。如果一份内容需要部门内多人点头才作数、要版本治理和复核日期，那是场景五。

标准目录：

```
team-wiki/
├── AGENTS.md              # 处理规则：怎么归位、怎么答、什么该拒绝
├── raw/
│   └── meetings/          # 评审会、争论记录、定规范的原始讨论
└── wiki/
    ├── index.md
    ├── log.md
    ├── concepts/          # 规则、标准、术语：一页一条，每条写清依据
    ├── cases/             # 好案例、坏案例、边界案例
    ├── outputs/           # 对外成品：手册、准则、检查清单、培训材料
    ├── rules/             # 由 outputs/ 编译出的规则块，禁止手改
    ├── thoughts/          # 规则该怎么改、为什么之前那样定
    └── sources/           # 可选：外部资料及其解读
```

`concepts/` 与 `cases/` 必建，其余按需：没有对外成品不建 `outputs/`，不需要 Agent 预审不建 `rules/`，不摄入外部资料不建 `sources/`。

和场景一的关键区别是**双可读**——页面既要人能读，也要 Agent 能加载：

- 契约类页面：人读的表格 + fenced yaml 规则块
- 词典类页面：术语、用户真实说法、我的映射、适用场景、证据层级
- 案例页：关键教训 + 关联规则

`rules/` 是编译产物，由 `outputs/` 里的真源生成，供 Agent 直接加载，禁止手改。

**部门手册、上下游准则这类用户也走这里**，但有两个前提：有一个能回答"为什么这么定"的 owner（多人共识的制度也要指定裁决人），拿得出规则被正确执行和被违反过的案例。没有案例的规范只是一份制度文档——它属于普通写作，不需要这个结构。

### 场景三：决策分身型

把老板的判断体系变成组织资产。同时服务两个受众：员工侧做概念翻译，AI 侧做判断框架。

三栏概念页是核心结构：

| 老板原话 | Agent 理解 | 员工语言 |
|---|---|---|
| 逐字保留，语义锚 | 结构化的判断逻辑 | 能直接执行的表述 |

核心纪律是**归属与校验**：老板说过 ≠ 老板拍板 ≠ 组织已执行。主张必须挂说话人，Agent 把握不足的理解挂起在 `verification.md` 等老板确认。

### 场景四：项目协作型

给在办项目建可追溯的工作区。它补的是项目管理 / CRM / 订单系统的空白——那些系统只记结果（任务已完成、订单已发货），不记为什么变成这样。

```
projects/<项目名>/
├── README.md              # 驾驶舱：进展、卡点、阅读入口
├── 00_项目元信息.md       # 决策链、干系人、信息权威
├── 01-项目上下文/         # 客户资料 / 我方调研 / 资料解读 / 我方产品
├── 02-沟通记录/           # 会议原文 + 总结（同名成对）
├── 03_方案对齐.md         # 当前共识、关键决策、待确认
└── 04-解决方案输出/       # 定稿方案、报价、合同、验收单
```

核心是**过程与结果分离**：

- `02-沟通记录/` 存过程，只增不改
- `04-解决方案输出/` 存确定性输出，定稿即归档

三条纪律：过程只增不改、每次会议必须回写状态页、状态必须标 `compiled_through` 日期。

**适用边界**：项目数 3-10 个、以会议沟通为主要工作形式、有会议转写或纪要习惯。超过 10 个项目应该用项目管理系统；完全没有转写习惯，这个库会退化成一个空壳。

### 场景五：部门共建型

给整个部门用：制度、流程、标准、模板、案例、培训材料。它解决的具体病症是**同一个问题，部门里不同的人给出不同答案**——而且答案没有版本、没有负责人、过期了没人知道。

```
dept-wiki/
├── AGENTS.md
├── raw/                    # 原件：定规则的会议录音、原始材料（只增不改）
└── wiki/
    ├── index.md            # 按业务线 + 按角色两条视图
    ├── log.md
    ├── 01-制度/            # 能不能做：红线、权限、审批、保密
    ├── 02-流程/            # 谁在什么时候做什么
    ├── 03-标准/            # 做到什么程度算对：口径、验收标准、术语
    ├── 04-模板/            # 直接套用：表单、清单、汇报模板
    ├── 05-案例/            # 做对的、做错的、边界情况
    ├── 06-培训/            # 新人上手路径、高频问题
    └── 99-归档/            # 废止与被替代的版本
```

六类按**判断动作**切分，不按文档格式切分——一个人遇到问题时知道自己要做的判断，就能找到目录。业务线不作目录，作 frontmatter 的 `domain` 字段，否则六类 × 五个业务线会变成三十个空目录。

和场景二的根本差别是**多人共建 + 版本治理**。每条内容必须有 `type`、`status`、`owner`、`review_by`：

```yaml
type: 标准
domain: 交付
status: 生效          # 草案 / 评审中 / 生效 / 废止
version: 2.1
owner: 张三（交付负责人）
contributors: [李四, 王五]
effective_from: 2026-05-01
review_by: 2027-05-01
```

正文固定六段：一句话、适用范围（含不适用范围）、规则正文、判断依据、支撑案例、变更记录。

**准入四条**：换个人照做结论一致、有案例支撑、有 owner、有复核日期。不满足的内容留在个人库继续沉淀，不硬塞。

**部门库不收录个人库原文**。个人在自己库里整理好，把"这一条全部门都该按这个来"的部分提炼出来贡献，部门库只存提炼后的结果，用 `contributors` 和 `derived_from` 指回来源。私有判断、未成型的直觉不进部门库，所以部门库没有 `thoughts/` 这类目录。

### 场景六：开放定义型

兜底入口：前五类判断不了，或者你已经想好自己的组织方式（设备台账、菜谱、健身记录、课程笔记、家庭事务……）。

和前五类相反，它是**先访谈再判断**——不先贴标签，而是先问清目的、背景和具体用途，拿到结构化回答后再给建议：

> "你说的这些其实是场景二，理由是……。你如果更想按自己的方式来，也可以。"

结构开放到什么程度：只保留五个必需物（`raw/`、`wiki/`、`AGENTS.md`、`index.md`、`log.md`），顶层分类由访谈推导，2-4 个，用你自己的词命名。不预建 `concepts/`、`cases/` 这类系统分类。

约束只有三条底线：

- `raw/` 只增不改
- 每个页面能回溯来源
- `index.md` 与实况一致

这三条是"这个库还能被 Agent 维护"的最低条件，其余全部按你的用法来。生成前会先给你 2-3 个候选顶层结构（按时间 / 按对象 / 按流程）让你选，而不是直接建。

## wiki 结构参考

所有场景生成的都是同一套三层结构，差别只在 `wiki/` 里长什么样：

| 层 | 是什么 | 谁维护 |
|---|---|---|
| `raw/` | 原件：文章、录音转写、客户资料、截图 | 只增不改 |
| `wiki/` | 从原件提炼出的页面，加 `index.md` 与 `log.md` | Agent 维护，你审阅 |
| `AGENTS.md` | 处理规则：怎么归位、怎么回答、什么该拒绝 | 你定，Agent 执行 |

### wiki/ 下每个目录的语义

| 目录 | 放什么 | 出现场景 |
|---|---|---|
| `concepts/` | 规则、标准、术语、方法论，尽量一页一条 | 一、二、三 |
| `cases/` | 具体发生过的事：好案例、坏案例、完整项目 | 一、二、三 |
| `sources/` | 外部信源的摘要 | 一、二 |
| `thoughts/` | 还不成熟的判断和反思 | 一、二、三 |
| `entities/` | 反复出现的人、公司、产品 | 一 |
| `synthesis/` | 多信源交叉后的综合结论 | 一 |
| `outputs/` | 对外成品：手册、准则、检查清单、培训材料 | 一、二 |
| `rules/` | 机器可执行的规则块，由 `outputs/` 编译，禁止手改 | 二 |
| `decisions/` | 编号决策记录，含重开条件 | 三 |
| `methodology/` | 方法论骨架（填写表式） | 三 |
| `conversations/` | 对话 → 判断的转化记录 | 三 |
| `claims.md` `verification.md` `boundaries.md` | 主张台账、待校验清单、知识边界 | 三 |
| `projects/`（库根目录，不在 wiki 下） | 每个在办项目一个目录，五件套自包含 | 四 |
| `01-制度/` `02-流程/` `03-标准/` `04-模板/` `05-案例/` `06-培训/` | 按判断动作分六类，每条带 `status` 与 `owner` | 五 |
| `99-归档/` | 废止与被替代的版本，保留不删 | 五 |
| 自定义分类 | 按时间 / 对象 / 流程分的 2-4 个目录 | 六 |

### 一个例子：专家的判断怎么变成手册

场景二最容易被理解成"写制度"。区别在结构——制度是一个文件，这里的规范要能被案例解释、能被新情况推翻：

```
raw/
└── meetings/                      # 定规范时的评审会、争论记录
wiki/
├── concepts/
│   ├── 交付验收标准.md            # 条款 + 每条的依据
│   └── 需求受理口径.md
├── cases/
│   ├── 2026-03-验收返工.md        # 坏案例：标准没写清导致的后果
│   └── 2026-05-客户特批.md        # 边界案例：什么情况可以破例
└── outputs/
    └── 交付手册-v2.md             # 对外成品，引用上面的规则与案例
```

读者对手册某一条不服时，能点进案例看当时为什么这么定；规则要改时，也能反查是哪些案例支撑了它。只有 `outputs/` 而没有 `concepts/` 和 `cases/`，那还是一份普通文档。

这个例子是**一个人定、别人执行**的结构。如果这份手册要由几个人共同维护、需要版本与复核日期，就换成场景五的六类目录——条款进 `01-制度/` 或 `03-标准/`，案例进 `05-案例/`，成品进 `04-模板/`，并给每页补 `status` 与 `owner`。

### 不预建用不上的目录

`concepts/` 与 `cases/` 是场景一至三的地基，但如果你只消费外部信息（场景一）、只追项目过程（场景四）、建部门库（场景五）或自定义结构（场景六），就不要建用不上的目录。空目录会让 Agent 误判内容该往哪放，也会让你以为"还有东西没填"。

## 建出来长什么样

生成的知识库里最重要的文件是 `AGENTS.md`。它定义了你的 AI 之后怎么处理内容，而不是一份使用说明。

以场景四为例，`AGENTS.md` 会写明：

- 摄入一场会议时先对齐说话人，再写总结，再回写状态页
- 回答"现在什么情况"时必须先说状态编译到哪天
- 客户说过 / 我方理解 / 已确认，三者不能混成一句
- 不做任务分派和进度催办——那是项目管理系统的职责

随后每次你往里投料，AI 都按这份规则处理，而不是每次凭感觉。

## 三个工作流

生成的 `AGENTS.md` 里，所有场景共用同一套结构：

| 阶段 | Agent 做什么 | 你做什么 |
|---|---|---|
| **Ingest** | 新内容进来后怎么处理：归位原文 → 提炼 → 挂来源 → 回写状态 | 投料，抽看几页，判断提炼得对不对 |
| **Query** | 被问到时怎么回答：先读哪一层、必须标注什么、什么情况下说"不确定" | 用真实问题去问，答非所问就记下来 |
| **Lint** | 定期检查：索引与实况是否一致、有没有孤岛页面、状态是否过期 | 把反复出现的偏差改回 `AGENTS.md` |

六个场景的差异在于每个阶段的具体规则，不在于阶段本身。你的活儿始终是三样：投料、用结果、修规则。

## 核心设计

### 渐进式披露

`SKILL.md` 只有路由所需的信息（约 21KB），场景细节放在 `references/` 按需读取。安装后不会一次性把几万字塞进上下文。

### 访谈驱动

不直接给模板。每次只问 2-3 个问题，确认理解后再继续。访谈节奏比问题清单更重要——设计类沟通密度高，一次抛出十个问题，用户就会开始瞎答。

### 自包含

模板、脚本、配置全部打包在 skill 内。核心功能（文本处理、关联、检索）不依赖任何外部服务。

### 场景裁剪

`assets/index-template.md` 里用 HTML 注释标记了六组场景专属分类，`init-wiki.sh` 在建库时按场景自动裁剪——建出来的索引只包含当前场景的槽位，不需要手工删。

## 设计来源

三层结构（`raw/` / `wiki/` / `AGENTS.md`）、Ingest–Query–Lint 三个动作、`index.md` + `log.md` 双文件，来自 Andrej Karpathy 的《LLM Wiki》。

它的主张是：不要让 LLM 每次提问都从原件重新推导（那是 RAG 的做法），而是让它增量维护一个持久化的 wiki——新资料进来就整合进已有页面、更新索引、标记与旧结论的冲突。维护这件事人不愿做，LLM 的成本接近零。

原文只有几页，写得抽象，鼓励你丢给自己的 Agent 一起实例化。这个 Skill 把那份抽象落到六个场景上，并补了访谈这一层。

- 原文：<https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f#file-llm-wiki-md>

## 可选工具

### 会议记录

本地录音直接转录：

```bash
python3 scripts/transcribe-media.py ./meeting.m4a \
  --project-path ./hub \
  --out-dir projects/某项目/02-沟通记录 \
  -t "0903-需求对齐-原文"
```

已有平台转写（飞书妙记、Get笔记、得到大脑）不需要脚本，导出文本即可。两种情况都按 `references/meeting-sop.md` 的 7 步流程处理。

### 媒体摄入

处理播客、视频、公众号等外部内容：

```bash
bash scripts/setup-media-tools.sh
```

支持 12 个平台：微信公众号、小红书、小宇宙、飞书社区、抖音、B站、YouTube、TikTok、微博、知乎、X/Twitter、喜马拉雅。

需要 Python 3.9+、ffmpeg，以及首次运行时下载 faster-whisper 模型。

### 脚本初始化

有 bash 环境时可以直接建库，跳过手工创建目录：

```bash
bash scripts/init-wiki.sh <项目路径> <场景> [项目名或额外目录...]

# 例：建一个项目协作型知识库，项目骨架建在 projects/欧奇密码-儿童营养/
bash scripts/init-wiki.sh ~/project-hub project 欧奇密码-儿童营养
```

场景参数：`personal` / `organizational` / `boss` / `project` / `department` / `open`。

`department` 会自动建好六类内容目录与 `99-归档/`；`open` 只建 `raw/` 与 `wiki/`，顶层分类由访谈确定后作为额外目录传入。

## 常见问题

**Q：我有很多笔记，能直接导入吗？**
能，但不建议一次全导。先跑通一个项目或一个主题，让 Agent 按规则处理过一遍，再批量迁移。否则规则还没调对，问题会被放大几十倍。

**Q：生成的库要放 git 吗？**
建议放。版本历史是过程追溯的一部分，尤其是场景四——会议纪要的修改记录本身就是证据。

**Q：六个场景能不能混用？**
可以，但要有主场景。混合场景按"哪个最紧迫"判定主场景，副场景的内容用目录分层容纳，不要两套 AGENTS.md 并行。

**Q：为什么不直接用一个文件夹 + 几个说明文档？**
因为 Agent 需要**可执行的规则**，不是描述。文件夹结构告诉它东西放哪，`AGENTS.md` 告诉它拿到东西后怎么处理、什么情况下该拒绝、回答时必须标注什么。缺了后者，每次都要重新交代一遍。

**Q：场景四和项目管理系统冲突吗？**
不冲突，是补充。任务、工时、甘特图归项目管理系统；"这个决定是什么时候谁拍的、当时为什么这么定"归知识库。有人问下一步做什么，答案在项目管理系统；问为什么走到这一步，答案在这里。

## 这套做法在知识管理研究里的位置

上面这些选择不是凭空来的，知识管理研究里大多有对应的说法；反过来看，也能看出它没覆盖哪些部分。

**知识生命周期**：获取 → 组织编码存储 → 共享转移 → 应用创新 → 保护更新。本 Skill 每一环都有对应物：`raw/` 收原件、访谈把判断问出来；目录 + frontmatter + `index.md`；六个场景各自定义受众；Query 的答案可回写为新页面；`log.md` + Lint + 状态字段。多数库死在后两环，因为这两环没有即时回报。

**编码化 vs 人格化**（Hansen, Nohria & Tierney, 1999）：前者把知识从人身上剥离成文档和规则，让人去"查"；后者让知识留在专家身上，文档只负责指路。成本结构相反——编码化前期贵、复用几乎免费但容易僵化；人格化响应快、依赖具体的人、规模不经济。六个场景就是在这两条路之间选：一、二、五偏编码化，四偏过程留痕，三是"尽量编码 + 承认编码不全"（`verification.md`）。

**隐性知识**（Polanyi, 1966；Nonaka & Takeuchi, 1995）：能写下来的只是判断的一部分，其余靠案例页承接。所以场景二和场景五里 `cases/` 不是可选。

**四个学派**：技术学派（KMS、知识图谱、检索）、行为/人文学派（人、文化、激励、实践社区）、综合学派（人-流程-技术，P-P-T）、战略学派（知识即竞争优势、智力资本）。这个 Skill 站综合学派：流程做骨架，技术只用 markdown + git。

**智力资本**：人力、结构、关系三类。知识库只能造结构资本——把已有的判断从人身上搬到文件里，让它不随人员流动消失。它不改变人的能力，也不改善客户关系。

**不做的部分**：知识审计、CKO 治理、绩效测评、激励机制、权限与保密分级、知识图谱与向量检索。这些要么是组织级制度设计，要么该由你的网盘、仓库和合规流程承担。
