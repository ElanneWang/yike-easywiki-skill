# Easy Wiki Skill

从零搭建 LLM 知识库的引导 Skill。安装后说一句"我想搭建知识库"，它会通过结构化访谈搞清你的知识结构、受众和工作流，然后生成一套能被 AI Agent 长期正确维护的知识库。

不是模板分发器。同样的模板套在不同人身上，Agent 不知道按什么标准处理内容，库最后都会退化成文件堆。

---

## 为什么要先访谈

大多数人搭知识库失败，不是因为工具不好，是因为**没定义清楚三件事**：

- **谁是知识的主角**：自己的积累、要给别人用的规范、老板的判断、还是在办的项目
- **什么算合格的知识**：一段会议记录要整理到什么程度才算能用的资料
- **什么该拒绝**：哪些内容不该进库，进了会污染整个库

这三个问题不回答，Agent 只能靠猜。猜错了的表现是：你问它一个项目现在什么情况，它给你列出十份文件让你自己看。

所以这个 Skill 的核心动作不是生成目录，是**问出答案再生成**。

## 快速开始

### 1. 安装

```bash
npx skills add https://github.com/ElanneWang/yike-easywiki-skill.git
```

没有 npx 环境时，把整个目录复制到 skills 目录即可：全局用 `~/.claude/skills/`（或对应工具的 skills 目录），只给当前项目用就放到项目的 `.agents/skills/` 下。复制后确认 `SKILL.md` 在目录第一层，不要多套一层文件夹。

### 2. 触发

在你的 AI 编码工具里打开任意目录（新建一个空目录最好），说：

> 我想搭建一个知识库

### 3. 跟着访谈走

Skill 会先问 4-5 个问题判断场景，再针对场景深入访谈 3-5 轮。整个过程通常 20-40 分钟。

访谈中会做两件事：

- **要真实材料**：不是让你描述需求，是让你给一份真实的会议转写、文章、或文档
- **当场跑一遍**：用你给的材料走完整摄入流程，让你看见机制怎么运转，而不只是听描述

访谈结束后你会得到一个可以直接用 git 管理的知识库目录，里面包含 `AGENTS.md`——这份文件决定了你的 AI 之后怎么维护这个库。

## 五种场景

场景判断的问题是：**这个知识库的主角是谁，或者是什么？**

| 场景 | 知识的主角 | 适用人群 | 解决什么 |
|------|-----------|---------|---------|
| 一、个人产能型 | 我 | 研究者、创业者、投资人、创作者 | 消费的外部信息沉淀成自己的判断 |
| 二、协作预审型 | 我 + 我的下游 | 产品经理、研发、销售、专业顾问 | 我的判断变成别人能直接用的规范 |
| 三、决策分身型 | 老板 | 创始人/一把手，及其助理、顾问 | 老板的判断体系变成组织资产 |
| 四、项目协作型 | 一件在办的事 | 售前、咨询、知识服务、定制交付 | 项目过程可追溯，状态不依赖个人记忆 |
| 五、开放定义型 | 你自己定义 | 前四类都不像的个人用途 | 按你自己的理解建库，只保留三条底线 |

### 场景一：个人产能型

给知识库自己用：看的文章、听的播客、做的实验、想到的点子，最后合成自己的判断和产出。

```
wiki/
├── concepts/      # 概念页：一个概念一页，标注来源和我的理解
├── cases/         # 案例页：发生了什么、为什么重要
├── sources/       # 信源摘要：每篇文章/播客的提炼
├── thoughts/      # 个人思考：不成熟的判断也留存
├── entities/      # 实体：反复出现的人、公司、产品
├── synthesis/     # 综合分析：多个信源交叉后的结论
└── outputs/       # 产出文档
```

### 场景二：协作预审型

给自己的下游用：把专业判断写成别人能直接执行的规则、检查清单、术语表。

和场景一的关键区别是**双可读**——页面既要人能读，也要 Agent 能加载：

- 契约类页面：人读的表格 + fenced yaml 规则块
- 词典类页面：术语、用户真实说法、我的映射、适用场景、证据层级
- 案例页：关键教训 + 关联规则

`rules/` 是编译产物，由 `outputs/` 里的真源生成，供 Agent 直接加载，禁止手改。

### 场景三：决策分身型

把老板的判断体系变成组织资产。同时服务两个受众：员工侧做概念翻译，AI 侧做判断框架。

三栏概念页是核心结构：

| 老板原话 | Agent 理解 | 员工语言 |
|---|---|---|
| 逐字保留，语义锚 | 结构化的判断逻辑 | 能直接执行的表述 |

核心纪律是**归属与校验**：老板说过 ≠ 老板拍板 ≠ 组织已执行。主张必须挂说话人，Agent 把握不足的理解挂起在 `verification.md` 等老板确认。

### 场景四：项目协作型

给在办项目建可追溯的工作区。它补的是项目管理 / CRM / 订单系统的空白——那些系统只记结果（任务已完成、订单已发货），不记为什么变成这样。

```
projects/<项目名>/
├── README.md              # 驾驶舱：进展、卡点、阅读入口
├── 00_项目元信息.md       # 决策链、干系人、信息权威
├── 01-项目上下文/         # 客户资料 / 我方调研 / 资料解读 / 我方产品
├── 02-沟通记录/           # 会议原文 + 总结（同名成对）
├── 03_方案对齐.md         # 当前共识、关键决策、待确认
└── 04-解决方案输出/       # 定稿方案、报价、合同、验收单
```

核心是**过程与结果分离**：

- `02-沟通记录/` 存过程，只增不改
- `04-解决方案输出/` 存确定性输出，定稿即归档

三条纪律：过程只增不改、每次会议必须回写状态页、状态必须标 `compiled_through` 日期。

**适用边界**：项目数 3-10 个、以会议沟通为主要工作形式、有会议转写或纪要习惯。超过 10 个项目应该用项目管理系统；完全没有转写习惯，这个库会退化成一个空壳。

### 场景五：开放定义型

兜底入口：前四类判断不了，或者你已经想好自己的组织方式（设备台账、菜谱、健身记录、课程笔记、家庭事务……）。

和前四类相反，它是**先访谈再判断**——不先贴标签，而是先问清目的、背景和具体用途，拿到结构化回答后再给建议：

> "你说的这些其实是场景二，理由是……。你如果更想按自己的方式来，也可以。"

结构开放到什么程度：只保留五个必需物（`raw/`、`wiki/`、`AGENTS.md`、`index.md`、`log.md`），顶层分类由访谈推导，2-4 个，用你自己的词命名。不预建 `concepts/`、`cases/` 这类系统分类。

约束只有三条底线：

- `raw/` 只增不改
- 每个页面能回溯来源
- `index.md` 与实况一致

这三条是"这个库还能被 Agent 维护"的最低条件，其余全部按你的用法来。生成前会先给你 2-3 个候选顶层结构（按时间 / 按对象 / 按流程）让你选，而不是直接建。

## 建出来长什么样

生成的知识库里最重要的文件是 `AGENTS.md`。它定义了你的 AI 之后怎么处理内容，而不是一份使用说明。

以场景四为例，`AGENTS.md` 会写明：

- 摄入一场会议时先对齐说话人，再写总结，再回写状态页
- 回答"现在什么情况"时必须先说状态编译到哪天
- 客户说过 / 我方理解 / 已确认，三者不能混成一句
- 不做任务分派和进度催办——那是项目管理系统的职责

随后每次你往里投料，AI 都按这份规则处理，而不是每次凭感觉。

## 三个工作流

生成的 `AGENTS.md` 里，所有场景共用同一套结构：

| 阶段 | 做什么 |
|------|--------|
| **Ingest** | 新内容进来后怎么处理：归位原文 → 提炼 → 挂来源 → 回写状态 |
| **Query** | 被问到时怎么回答：先读哪一层、必须标注什么、什么情况下说"不确定" |
| **Lint** | 定期检查：索引与实况是否一致、有没有孤岛页面、状态是否过期 |

五个场景的差异在于每个阶段的具体规则，不在于阶段本身。

## 核心设计

### 渐进式披露

`SKILL.md` 只有路由所需的信息（约 21KB），场景细节放在 `references/` 按需读取。安装后不会一次性把几万字塞进上下文。

### 访谈驱动

不直接给模板。每次只问 2-3 个问题，确认理解后再继续。访谈节奏比问题清单更重要——设计类沟通密度高，一次抛出十个问题，用户就会开始瞎答。

### 自包含

模板、脚本、配置全部打包在 skill 内。核心功能（文本处理、关联、检索）不依赖任何外部服务。

### 场景裁剪

`assets/index-template.md` 里用 HTML 注释标记了五组场景专属分类，`init-wiki.sh` 在建库时按场景自动裁剪——建出来的索引只包含当前场景的槽位，不需要手工删。

## 测试

`evals/evals.json` 是行为测试用例，覆盖五个场景的路由、混合场景的优先级判定、"不该触发"的边界，以及典型的边界情况（如老板只给了 Excel 框架、用户没有会议转写习惯、开放场景其实属于场景二）。

修改 `SKILL.md` 或任何 `references/scenario-*.md` 之后跑一遍，确认路由没有退化——尤其是场景二与场景四、场景一与场景三这两对容易混的判断。

## 可选工具

### 会议记录

本地录音直接转录：

```bash
python3 scripts/transcribe-media.py ./meeting.m4a \
  --project-path ./hub \
  --out-dir projects/某项目/02-沟通记录 \
  -t "0903-需求对齐-原文"
```

已有平台转写（飞书妙记、Get笔记、得到大脑）不需要脚本，导出文本即可。两种情况都按 `references/meeting-sop.md` 的 7 步流程处理。

### 媒体摄入

处理播客、视频、公众号等外部内容：

```bash
bash scripts/setup-media-tools.sh
```

支持 12 个平台：微信公众号、小红书、小宇宙、飞书社区、抖音、B站、YouTube、TikTok、微博、知乎、X/Twitter、喜马拉雅。

需要 Python 3.9+、ffmpeg，以及首次运行时下载 faster-whisper 模型。

### 脚本初始化

有 bash 环境时可以直接建库，跳过手工创建目录：

```bash
bash scripts/init-wiki.sh <项目路径> <场景> [项目名或额外目录...]

# 例：建一个项目协作型知识库，项目骨架建在 projects/欧奇密码-儿童营养/
bash scripts/init-wiki.sh ~/project-hub project 欧奇密码-儿童营养
```

场景参数：`personal` / `organizational` / `boss` / `project` / `open`。

## 常见问题

**Q：我有很多笔记，能直接导入吗？**
能，但不建议一次全导。先跑通一个项目或一个主题，让 Agent 按规则处理过一遍，再批量迁移。否则规则还没调对，问题会被放大几十倍。

**Q：生成的库要放 git 吗？**
建议放。版本历史是过程追溯的一部分，尤其是场景四——会议纪要的修改记录本身就是证据。

**Q：五个场景能不能混用？**
可以，但要有主场景。混合场景按"哪个最紧迫"判定主场景，副场景的内容用目录分层容纳，不要两套 AGENTS.md 并行。

**Q：为什么不直接用一个文件夹 + 几个说明文档？**
因为 Agent 需要**可执行的规则**，不是描述。文件夹结构告诉它东西放哪，`AGENTS.md` 告诉它拿到东西后怎么处理、什么情况下该拒绝、回答时必须标注什么。缺了后者，每次都要重新交代一遍。

**Q：场景四和项目管理系统冲突吗？**
不冲突，是补充。任务、工时、甘特图归项目管理系统；"这个决定是什么时候谁拍的、当时为什么这么定"归知识库。有人问下一步做什么，答案在项目管理系统；问为什么走到这一步，答案在这里。
