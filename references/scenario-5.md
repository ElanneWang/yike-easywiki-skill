# 场景五：部门共建型（部门知识库）

## 场景定义

部门知识库不是"更大的个人库"，也不是"更多人的场景二"。它解决的是一个具体病症：**同一个问题，部门里不同的人给出不同答案**——而且答案没有版本、没有负责人、过期了没人知道。

主语是**部门**，不是某个人。

### 与场景二的分界

场景二也是"给别人用的规范"，所以这两个场景最容易混。判据只有一个：**这条内容需要几个人点头才算数？**

| | 场景二：业务专家型 | 场景五：部门共建型 |
|---|---|---|
| 主语 | 我 | 部门 |
| 权威来源 | 单点权威：一个人定，别人执行 | 多人共建：几个人的判断合成一个口径 |
| 关键动作 | 把我的判断写清楚 | 从多个人的贡献里筛出共识 |
| 版本治理 | 不需要，改了就改 | 必需，`status` + `version` + `review_by` |
| 典型产物 | 一份交付规范、一个术语表、一套审核清单 | 部门手册全集、新人上手路径、制度库 |

一句话：一个人定、别人执行 → 场景二（`references/scenario-2.md`）；多人的判断要合成一个口径 → 场景五。

### 部门库与个人库的关系

部门库的内容**来自**个人库，但不收录个人库原文。

- 个人在自己库里整理好，把"这一条我认为全部门都该按这个来"的部分提炼出来贡献
- 部门库只存提炼后的结果，用 `contributors` 和 `derived_from` 指回贡献者与来源页面
- 个人库里的私有判断、未成型的直觉、只对某个人有效的技巧，**一律不进部门库**

所以部门库不设 `thoughts/`、`synthesis/` 这类个人思考目录。

## 典型用户与触发信号

典型用户：部门负责人、制度/流程的维护人（运营、质量、HR、交付经理）、带 5-20 人团队的 leader。

出现这些信号时优先考虑场景五：

- 手册散在多个网盘和微信群里，没人知道哪份是现行的
- 新人上手靠问人，同一个问题问三个人得到三个答案
- 制度是两年前定的，业务已经变了，但没人负责改
- 出现纠纷时找不到"当时为什么这么定"

## 访谈流程（5 步）

每次只问一组，等回答再继续。每一步都要给即时反馈，反馈固定三类：**归属**（这条该放哪一类）、**状态**（草案还是生效、谁定的）、**缺口**（缺 owner、缺案例、缺适用范围）。

### 第一步：这个部门是干什么的

1. 部门有几个人，分成几个职能块（比如品牌、投放、内容）？
2. 部门对外交付什么？谁的验收决定你们做得好不好？
3. 哪些事是"必须按规矩来"的，哪些是"看情况判断"的？

即时反馈示例：

> 归属：你刚才说的"素材归档命名"属于**标准**，不是制度——它约束的是质量，不是许可。
> 缺口：你提到了三个职能块，但没说清谁对哪块有最终解释权。

### 第二步：现在大家靠什么找东西

1. 现在这些规范、模板、案例存在哪里？（网盘 / 飞书 / 群消息 / 老员工脑子）
2. 上一次有人找不到东西、或者用错版本，是什么时候？后果是什么？
3. 现在如果两个人对同一件事给出不同口径，最后听谁的？

这一步的目的是拿到**真实痛点**，不是收集抱怨。追问"最近一次具体是什么事"。

即时反馈示例：

> 状态：你说的"听老张的"说明现在权威是人而不是文档——这正好是这个库要解决的第一件事。
> 缺口：如果老张离职，这些判断有没有落到纸面？

### 第三步：最常被问到的五个问题

1. 新人进来最常问的五个问题是什么？
2. 客户或上下游最常问的三个问题是什么？

这十个问题直接决定 `06-培训/` 和 `03-标准/` 的内容。问完当场分类：哪些是"查一下就知道"（→ 标准/流程），哪些是"要人判断"（→ 案例 + 判断依据）。

即时反馈示例：

> 归属："报价谁来批"是**制度**（权限问题），"报价怎么算"是**标准**（口径问题），要拆成两页。
> 缺口：这五个问题里三个没有对应文档，说明现在完全靠口传。

### 第四步：哪些必须遵守，哪些只是建议

1. 哪些内容违反了要追责？哪些只是"建议这么做"？
2. 每条内容的最终解释人是谁？他换岗了谁接？
3. 制度多久复核一次？一年还是半年？

这一步决定两件事：`01-制度/` 与 `03-标准/` 的分界，以及每个页面的 `owner` 和 `review_by`。

即时反馈示例：

> 状态：这三条你说是"必须"，但只有一条有明确的追责方式，另外两条其实是建议——建议放标准，不要放制度。
> 缺口：五个职能块里有三个没有指定解释人，这些页面上线后没人维护。

### 第五步：拿一份真实材料跑一遍

让用户给一份**现行**的制度、SOP 或模板（不要给草稿），当场走完整流程：

1. 判断它属于六类中的哪一类
2. 拆成一页或多页（一份手册通常要拆，别整篇塞进去）
3. 补 frontmatter：`type` / `domain` / `scope` / `status` / `version` / `owner` / `review_by`
4. 补"判断依据"和"支撑案例"——用户说不出来就标为缺口，不要编
5. 给出归档规则：这一版生效后，旧版移入 `99-归档/` 还是就地标注废止

跑完这一份，用户就知道自己的材料要拆到什么粒度。

## 目录推导

六类按**判断动作**切分，不按文档格式切分：

```
dept-wiki/
├── AGENTS.md
├── README.md
├── raw/                    # 原件：定规则的会议录音、原始材料（只增不改）
└── wiki/
    ├── index.md            # 导航：按业务线 + 按角色两条视图
    ├── log.md
    ├── 01-制度/            # 能不能做：红线、权限、审批、保密
    ├── 02-流程/            # 谁在什么时候做什么：SOP、跨角色交接
    ├── 03-标准/            # 做到什么程度算对：口径、验收标准、术语
    ├── 04-模板/            # 直接套用：表单、清单、汇报模板
    ├── 05-案例/            # 做对的、做错的、边界情况
    ├── 06-培训/            # 新人上手路径、高频问题
    └── 99-归档/            # 废止与被替代的版本
```

为什么这样分：一个人遇到问题时不知道自己该去哪个目录，是因为目录按"部门有哪些科室"分；按"我要做的是一个什么判断"分，就能找到。

### 一条主维度原则

**业务线不作目录，作字段。**

六类 × 五个业务线会变成三十个空目录，没人维护。所以：

- 目录只按内容类型分
- 业务线放进 frontmatter 的 `domain`
- `wiki/index.md` 维护一张按业务线聚合的表，指向同一批页面

只有部门大到超过百篇、且各业务线内容几乎不交叉时，才在类型目录下再按业务线分一层。

三种规模的处理：

| 规模 | 目录 | 字段 |
|---|---|---|
| 单职能小部门（<10 人） | 六类 + 归档，`06-培训/` 可先只建一页 | `domain` 可省略 |
| 多职能部门 | 六类 + 归档 | `domain` 必填，`index.md` 按域聚合 |
| 事业部 | `类型/业务线/` 两层 | `domain` 与目录保持一致 |

## 页面结构

部门库的页面比个人库多三项必备信息：谁负责、现在是否有效、什么时候该复核。

```yaml
---
title: 交付验收标准
type: 标准                 # 制度 | 流程 | 标准 | 模板 | 案例 | 培训
domain: 交付               # 业务线 / 职能域
scope: 全部门              # 全部门 | 某业务线 | 某角色
status: 生效               # 草案 | 评审中 | 生效 | 废止
version: 2.1
owner: 张三（交付负责人）
contributors: [李四, 王五]   # 这条是谁贡献的判断，出分歧找谁
derived_from: [张三个人库/交付验收口径]
effective_from: 2026-05-01
review_by: 2027-05-01
---
```

正文骨架固定六段：

1. **一句话** — 这条讲什么，做不到就翻页
2. **适用范围** — 管谁、不管谁（写清不适用范围比写适用范围更有用）
3. **规则正文** — 条款式，可被 Agent 直接加载做预审
4. **判断依据** — 为什么这么定，这是个人贡献最关键的部分
5. **支撑案例** — 链接 `05-案例/`，至少一个好案例一个坏案例
6. **变更记录** — 谁在什么时候因为什么改的

第 4 段和第 5 段是部门库与"制度汇编"的分水岭。只有条款没有依据的页面，两年后没人敢改。

## 准入四条

部门库不接收"写得好"的内容，只接收满足条件的内容：

1. 换个人照做，结论应该一致
2. 有案例支撑，不是凭印象
3. 有 owner，出问题找得到人
4. 有复核日期，制度会过期

不满足就先放 `01-制度/` 之外，或者留在个人库继续沉淀，不硬塞。

## AGENTS.md 必须写清的六件事

模板见 `references/templates.md` 的场景五部分。生成时必须写清：

1. 每条内容必须有 `type`、`status`、`owner`，缺一项视为不完整页面
2. 不接收个人未定稿观点、个人偏好、只对单人有效的技巧
3. 改内容必须写变更记录；不覆盖旧版本，废止版本移入 `99-归档/`
4. 回答"现在按什么执行"时先看 `status`，只能引用 `status: 生效`
5. `review_by` 过期的页面主动提醒复核，不自动续期
6. 不做任务分派、绩效评价、审批流执行——那是 OA 和项目管理系统的职责

## 边界情况

| 情况 | 处理 |
|---|---|
| 部门只有 3 人，且只有一个人懂 | 先走场景二（`references/scenario-2.md`），人多到需要交接时再升级 |
| 没有任何现成文档，全靠口头 | 先访谈把口头规则写进 `03-标准/`，再逐步补 `01-制度/`，不要一上来就"制定制度" |
| 老板就是部门负责人 | 场景三与场景五并存：老板拍板进 `decisions/`，团队确认后的口径进 `01-制度/` 或 `03-标准/` |
| 内容涉密、需要分级 | 用 `scope` + 保密字段，`raw/` 不参与外网同步；涉密页仍要留 owner 与复核日期 |
| 已有飞书/SharePoint 知识库 | 迁移而非重建：先搬制度与模板，案例和培训后补；旧库设为只读 |
| 用户想按人分目录（"小王负责的""小李负责的"） | 拒绝，按内容类型分；人用 `owner` 字段表达 |
| 用户想把它当项目管理系统用 | 拒绝，转场景四（`references/scenario-4.md`） |
| 两个部门口径冲突 | 本库只记本部门口径，用 `scope` 标明；跨部门共识另建一层或标为待协调 |

## 生成后要交代的三条纪律

- `status` 必填：没有状态的内容等于没有效力
- 变更留痕：改了什么、为什么改、谁批的
- 归档不删：废止的版本移入 `99-归档/`，保留链接，否则同一个问题会被反复重新讨论
