# 场景五：开放定义型（自带结构）

## 场景定义

这是**兜底入口**，不是第五种"知识主角"。

前四个场景都是先判断再访谈：知道主角是谁（我 / 我+下游 / 老板 / 一件在办的事），就知道该问什么。场景五反过来——**先访谈，再判断**。用户可能：

- 明确知道自己要什么结构（"我想按客户分""我已经有目录了，帮我改成 Agent 能维护的"）
- 描述的内容归不进前四类（家庭事务、设备台账、菜谱、健身记录、个人收藏、课程笔记、病史记录……）
- 同时带多种特征，且本人有明确主张

这三种情况的共同点是：**不要用前四场景的模板去套他**。场景五的职责是把用户脑子里的结构翻译成 Agent 能执行的规则，而不是给他一个更好的结构。

### 与前四场景的关系

| | 前四场景 | 场景五 |
|---|---|---|
| 顺序 | 先判断场景，再按场景访谈 | 先访谈，拿到目的和背景，再给判断 |
| 结构来源 | 场景模板 + 访谈填充 | 用户自带 + 访谈推导 |
| 强制约束 | 各自的关联链与纪律 | 只有三条底线 |
| 失败方式 | 套错场景，用户用不下去 | 放手太多，库没有规则、Agent 无法维护 |

场景五最大的风险不是"结构不够好"，而是**变成一个没有规则的文件夹**。所以它虽然开放，但必须保留最小骨架和三条底线。

## 第一步：先问目的，不要先贴标签

开场不要宣布"你属于开放场景"。先问清楚三件事，一次问完，等回答：

1. 你想用这个库解决什么具体问题？现在这件事是怎么处理的、哪里卡住了？
2. 里面大概会放哪些东西？给我三个真实的例子（不要类型名词）。
3. 除了你，还有谁会看？他们看的时候想解决什么？

拿到结构化回答后，**先给判断，再动手**：

> "你说的这些——三类客户都问同样的问题、你要让销售自己查——这其实是场景二（协作预审型）。我建议按场景二组织，因为它已经有现成的双可读结构。你如果更想按自己的方式分，也可以，我按你说的来。"

判断依据：

| 回答里出现这些信号 | 建议 |
|---|---|
| 内容是给下游/同事用的规范、话术、检查清单，跨项目复用 | 回退场景二 |
| 有客户、有进度、有交付节点，要追溯"为什么这么定" | 回退场景四 |
| 主角是某位老板/创始人的判断体系 | 回退场景三 |
| 主要消费外部信息，产出给自己看 | 回退场景一 |
| 都不命中，或用户坚持自己的结构 | 留在场景五 |

判断要带理由，也要允许被推翻。用户说"我就想按自己的来"，就按他的来——这是场景五存在的意义。

## 第二步：访谈（5 步）

每一步都要给即时反馈。反馈固定三类，各一两句：

- **归属**：这条东西以后放哪
- **维度**：它属于哪个分类维度（时间 / 对象 / 流程 / 主题）
- **缺口**：还差什么才能用（没有真实例子 / 没有查找场景 / 边界没定）

### 第 1 步：目的与现状

1. 现在这些内容放在哪？为什么想换？
2. 最近一次你需要找某样东西、但没找到，是什么情况？

访谈目的：找到**真实的痛点场景**。"文件太乱"不是痛点，"上次客户问起三个月前定的报价依据，我翻了四个地方"才是。

即时反馈：

- "你现在的做法是 X，卡在 Y——这个卡点决定后面要建哪一种索引"
- 如果用户说不出痛点，只是"想整理一下"：提醒他，没有痛点就没有判断标准，库会建得很漂亮但没人用；建议先从一个具体的痛点开始

### 第 2 步：三个真实例子

1. 给我三个具体的例子——不是"行业资料"这种类别，是"这份文件""这条笔记""这次记录"。
2. 这三样东西之间有共同点吗？你平时会把它们放一起吗？

访谈目的：从真实材料反推维度，而不是从用户自述的领域反推。

即时反馈：

- 三样东西能归到同一维度 → 告诉他"你的自然维度是 X，我们就按这个建"
- 三样东西互不相干 → 说明现在只有一个维度（时间），不要硬造分类

### 第 3 步：怎么找（决定索引维度）

1. 假设三个月后你要找其中一样东西，你会先想起什么？时间、客户名、项目名、还是关键词？
2. 你会不会把同一条信息同时归到两个地方？

访谈目的：**人按"怎么想起它"找，不按"它属于哪一类"找**。这一步决定目录和索引怎么建，比"内容分类"更重要。

即时反馈：

- "你说会先想起时间 → 顶层就按年份或月份分，不要按主题分"
- "你说会同时想起客户和时间 → 只选一个做主维度，另一个用标签或索引页交叉"
- "你说想两个地方都放一份 → 不要复制文件，用链接或索引页指向唯一一份"

### 第 4 步：谁看 + 什么不该进来

1. 除了你，还有谁看？他们需要看到全部，还是只看一部分？
2. 有哪些东西你**不**想放进来？（涉密、临时、别人给的还没验证的、情绪化的）

访谈目的：前者决定写作风格（要不要双可读），后者决定 AGENTS.md 的拒绝清单。

即时反馈：

- "只有你自己看 → 不要求双可读，页面可以写得随意，但来源必须留"
- "别人也看 → 至少要有 index 和一个'新人从哪读起'的入口"
- "你说涉密的不放 → 这条要写进 AGENTS.md，让 Agent 主动拒绝"

### 第 5 步：把你的现有结构当种子

1. 你现在有没有已经在用的目录、表格、标签体系？发我看一眼。
2. 这里哪些是你觉得好用的、哪些是你早就想改掉的？

访谈目的：拿现有结构当种子，比从零设计更容易被用户接受，也更容易发现"他嘴上说按主题分，实际文件都按日期命名"这类偏差。

然后在生成前，**给 2-3 个候选顶层结构让用户选**，不要直接建：

```
候选 A：按时间
  wiki/2026/、wiki/2025/ ...

候选 B：按对象
  wiki/<客户名>/、wiki/<设备名>/ ...

候选 C：按流程
  wiki/01-收集/、wiki/02-处理/、wiki/03-产出/ ...
```

每个候选说一句适用条件和一个缺点。用户选完再建，避免建完才发现维度选错——改维度的成本远高于多问一句。

## 结构推导规则

| 访谈信号 | 推导结果 |
|---------|---------|
| 用户主要靠时间回忆 | 顶层按年/月分，索引按主题标签 |
| 用户主要靠对象回忆（客户、设备、人） | 顶层按对象分，一个对象一个目录 |
| 用户说的是流程（收集→处理→产出） | 顶层按阶段分，页面里标阶段 |
| 用户只有主题，没有别的维度 | 顶层按主题分，但不超过 4 个，多了会空 |
| 三个例子互不相干、也说不出维度 | 只建 `wiki/notes/` 一层，用起来再长 |
| 用户已有可用结构 | 直接沿用他的命名，只补 `raw/`、`index.md`、`log.md` 和 AGENTS.md |

硬规则：

- **顶层分类 2-4 个**，超过 4 个说明维度混了，回头重选
- **命名用用户自己的词**，不要换成"概念/案例/实体"这类系统语言
- **不为空分类建目录**，先建一层，长出来再拆
- **不预置前四场景的目录**（concepts/cases/projects 等），除非用户自己要求

## 三条底线

写进 AGENTS.md，不可省略。这是场景五唯一的强制项，用来保证这个库还能被 Agent 维护：

### 底线一：raw 只增不改

原始材料（截图、录音、导出文件、别人发来的文档）进 `raw/` 后不改写。要修正就在 wiki 页面里写，并标明与原文的差异。

### 底线二：每个页面能回溯来源

wiki 页面的 frontmatter 必须有 `sources:`，指向 `raw/` 里的具体文件，或写明"来自口述，YYYY-MM-DD"。没有来源的页面，Agent 在 Lint 时要标出来。

### 底线三：index 与实况一致

`wiki/index.md` 是入口，不是装饰。Ingest 后必须更新，Lint 时必须核对。索引和目录对不上，开放结构就会迅速失控。

## AGENTS.md 装配方式

场景五没有固定模板，用**通用骨架 + 三段填空**装配：

```markdown
# <库名> 维护规则

## 角色定义
你是 <库名> 的知识库 Agent。这个库服务于 <目的>，主要读者是 <读者>。
你的职责是：归属、提炼、保持索引准确。

## 目录结构
<由访谈推导的 2-4 个顶层分类，每个一句话说明放什么>

## 归属规则（填空）
- <什么内容 → 放哪个目录>
- <同一内容有两种归属时，以什么为准>
- <原件与整理稿的关系>

## 检索路径（填空）
- 被问到 <某类问题> 时，先读 <哪一层>，再读 <哪一层>
- 回答时必须标注 <来源/时间/不确定>

## 拒绝清单（填空）
- 不接收：<用户明确排除的内容>
- 不推测：<没有来源的判断>
- 不覆盖：<定稿/原件>

## 工作流
Ingest：归位原件 → 提炼 → 挂 sources → 更新 index 和 log
Query：先读 index 定位 → 读对应页面 → 回答并标注来源
Lint：索引与实况不一致 / 无来源页面 / 断链 / 过期内容

## 三条底线
1. raw 只增不改
2. 每个页面能回溯来源
3. index 与实况一致
```

三段填空必须来自访谈原话，不能留空，也不能填成通用套话。"归属规则"至少要有一条是用户自己说过的判断（比如"客户给的原件一律不改，我的分析另存"）。

## 边界情况处理

| 情况 | 处理方式 |
|------|---------|
| 用户说不出目的，只想"整理一下" | 给一个具体痛点问题让他回忆，仍说不出来就先不建库，先记录一周 |
| 用户坚持要一个前四场景里明显更合适的结构 | 说明一次利弊，然后按用户的来——场景五允许被推翻 |
| 用户拿来的结构有 8 个顶层分类 | 先合并到 4 个以内，说明"分类多了会空"；不接受就先按原样建，但 Lint 时提示 |
| 用户想全部塞进一个文件夹 | 可以，只建 `wiki/notes/`，但要求文件名带日期或对象前缀，否则三个月后找不到 |
| 内容涉密 | 建议独立 git 仓库、单独控制访问；拒绝清单里写明 |
| 用户没有 raw 原件，只有整理过的笔记 | 仍适用，`sources:` 写"来自个人笔记，YYYY-MM-DD"，并标 `unverified` |
| 用户要的是给别人看的成品，不是知识库 | 这是内容创作请求，不建库；直接帮他写 |
| 用户中途发现其实属于场景二/四 | 立即切换，保留已收集的访谈结果，不要重新问一遍 |

## 访谈结果记录

```yaml
场景: 开放定义型知识库
目的: [要解决的具体问题]
痛点场景: [最近一次找不到东西的情况]

# 内容
三个例子: [文件/笔记/记录的具名例子]
共同维度: [时间/对象/流程/主题/无]

# 使用
查找方式: [先想起什么]
读者: [只有自己/还有谁]
边界: [什么不放进来]

# 结构
现有结构: [目录/表格/标签，或"无"]
选定顶层维度: [A 时间/B 对象/C 流程/D 主题/E 单层]
顶层分类: [2-4 个目录名，用用户原词]
拒绝清单: [N 条]
```
