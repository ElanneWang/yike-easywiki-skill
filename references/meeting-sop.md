# 会议记录处理 SOP

## 何时用本文件

输入是**一场会议的转写或录音**时用。产出是两份文件，同名成对：

- `{MMDD}-{主题}-原文.md`：转写原文，原样保存
- `{MMDD}-{主题}-总结.md`：按本 SOP 整理的结构化纪要

两份都放项目的 `02-沟通记录/` 下。**原文不改，总结可迭代。**

## 完整工作流（7 步）

### Step 1：定位原文

确认转写文件在哪里、覆盖哪段时间、是不是完整。

- 本地录音：先跑转写（见下方「转写脚本」）
- 平台转写（飞书妙记、Get笔记、得到大脑）：导出文本，直接当原文
- 人工记录：如果只有零散笔记，说明"这不是完整原文"，总结里要标注信息完整度

### Step 2：完整读取原文

读全文，不要只看开头。会议的价值常在后半段——前半段在客套和铺垫，结论往往在后三分之一。

**不要边读边写。** 先读完，形成整体印象。

### Step 3：与用户对齐前提信息

写文件之前先确认三件事，问一次即可：

1. **说话人映射**：说话人1/2/3 分别是谁？
2. **会议性质**：对齐型 / 评审型 / 同步型 / 探索型？
3. **这次会最要紧的是什么**：是要定方案、要决策、还是只是同步？

映射错了，整份纪要全错——这是最贵的一个坑，见下方「说话人身份映射」。

### Step 4：先输出时间序核心大纲

不要直接生成完整文件。先给用户一段大纲，确认结构对不对：

```
1. 00:00-08:30  {章节标题} —— {一句话摘要}
2. 08:30-20:10  {章节标题} —— {一句话摘要}
...
```

大纲被认可后再写正文。这一步能挡掉大部分返工。

### Step 5：创建文件并写入结构化总结

按下方「总结结构」写。一次写完整，不要留 TODO 占位。

### Step 6：迭代补充章节

第一遍写完后，回看原文，检查有没有漏掉的重要段落，追加章节。**追加不覆盖**。

### Step 7：验证文件状态

写完必须验证：

- 文件是否真的存在、行数是否合理（几百字的会不可能是两万行）
- 章节数是否与大纲一致
- 行动项是否每条都有责任人
- 具名实体有没有被泛化
- **有没有回写项目状态页**（场景四：`03_方案对齐.md`）

最后一项最容易被跳过，也最致命。

## 关键原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | 先对齐，再写文件 | 说话人和会议性质没确认，不要动笔 |
| 2 | 原话金句必须保留 | 逐字引用，前后加引号并挂说话人。金句是语义锚，防止后续理解漂移 |
| 3 | 时间序是骨架 | 按发生顺序，不按主题归类。过程的价值在演进 |
| 4 | 结构化优于长段落 | 表格、列表、加粗结论，不要大段流水叙述 |
| 5 | 行动项必须可执行 | 谁、何时、做什么，三要素缺一不可 |
| 6 | 每章带一句话摘要 | 供扫读和与平台妙记交叉验证 |
| 7 | 具名实体逐字保留 | 品牌、产品、人名不得泛化成"某品牌""某负责人"；与已有口径冲突时强制进「待核/差异」，不自行裁决 |
| 8 | 关键决策三段式 | 问题 → 方案 → 依据。缺依据的决策等于没记 |
| 9 | 单次写入必须验证 | 写完检查文件存在、行数、章节数 |

## 容易踩的坑

### 坑 1：说话人身份映射写反（最贵）

**场景**：一场会里两个人都姓"王"，转写把他们标成说话人1、说话人2，凭语感分配，结果全反了——整份纪要的归属全错。

**防法**：映射不能靠语感，必须用硬事实交叉验证：

| 验证角度 | 怎么用 |
|---------|--------|
| 年龄 | 提到"我们那个年代""刚毕业"能定位 |
| 公司 | 谁说"我们公司"、谁说"你们公司" |
| 地域人脉 | 提到共同认识的人、共同去过的地方 |
| 谁在给建议 | 给建议的一方通常是外部/顾问 |

四个角度中至少两个能对上，再确认映射。对不上就明确标"待确认"，不要猜。

### 坑 2：人名/产品名误写

转写会把品牌名、人名写错（同音字）。发现可疑的名称，在「待核/差异」里列出，不要直接在正文里改成你猜的版本。

### 坑 3：金句遗漏

会议里最有价值的是几句原话，整理时容易被"总结"掉。原话必须逐字保留。

### 坑 4：过度总结

把 40 分钟压成 3 句话，信息全丢了。总结应该压缩**冗余**而不是压缩**信息**。

### 坑 5：行动项模糊

"后续跟进"不是行动项。必须具体到人、时间、动作。

### 坑 6：写完不回写状态

纪要写完就结束，项目状态页没更新——下次有人问"现在什么情况"，Agent 还得去翻纪要。

## 会议类型与回写去向

| 类型 | 特征 | 回写位置 |
|------|------|---------|
| 对齐型 | 产生共识，明确了要做什么 | `03_方案对齐.md` 的当前共识 + 阶段性变更 |
| 评审型 | 产生决策，在几个方案里选了一个 | `03_方案对齐.md` 的关键决策（三段式） |
| 同步型 | 只更新进度，没有新结论 | `README.md` 的当前进展 + 变更日志 |
| 探索型 | 没有结论，只是聊 | 原文留存即可，不强行总结成纪要 |

## 转写脚本

本地录音或音视频文件可以直接转录：

```bash
python3 scripts/transcribe-media.py <本地文件或URL> \
  --project-path <库根目录> \
  --out-dir projects/<项目名>/02-沟通记录 \
  -t "0903-需求对齐-原文"
```

- **本地文件**：跳过下载，直接交给 faster-whisper
- **平台 URL**（B站/YouTube/小宇宙等）：先 yt-dlp 下载音频再转录
- **已有平台转写**（妙记/Get笔记）：不走脚本，直接导出文本，从 Step 3 开始

依赖安装见 `scripts/setup-media-tools.sh`。

## 命名规范

```
{MMDD}-{项目简称}-{会议主题}-原文.md
{MMDD}-{项目简称}-{会议主题}-总结.md
```

规则：

- 日期用 MMDD 四位，同年内不写年份（跨年时补年份）
- 主题用 6-15 个字概括会议目的，不用"沟通""讨论"这类无信息量的词
- 同一天多场会，主题必须能区分
- **原文与总结除后缀外完全同名**，靠这个保证配对不丢
