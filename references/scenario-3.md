# 场景三：决策分身型知识库（老板的第二大脑）

## 场景定义

知识库存在的目的是把老板（创始人/一把手）的判断体系变成组织资产。它同时服务两个受众，缺一不可：

- **员工侧 —— 概念翻译。** 老板用高度个人化的抽象语言描述生意，员工听不懂，每次沟通都要从头解释。知识库把老板的概念翻译成员工能执行的语言，压缩沟通成本。
- **AI 侧 —— 判断框架。** 老板的决策逻辑被抽取成结构化规则后，Agent 可以按老板的框架追问、推演、预审。让 AI 像老板一样思考，这是"决策分身"的工程含义。

典型用户画像：商业架构能力强的创始人/一把手。思考体系完整但高度个人化，用一套只有自己懂的词汇描述生意（自造词、内部缩写、只有少数人能解码的隐喻框架）。典型病症：员工听不懂、判断依赖老板本人在场、老板的只言片语被员工过度解读。

关键定位：本场景不是"给老板建笔记本"。这条链路过去由人肉顾问完成——多轮沟通抽取老板的思维体系、教老板使用 AI、最终产出知识包。本 skill 替代的正是"人肉教"这个环节，直接完成第二大脑的 onboarding。

与场景一的区别：用户说"我想建第二大脑"时，看大脑的主人是谁——自己的大脑给自己用（消费外部信息、个人积累）是场景一；把**老板的大脑**变成组织资产（概念翻译 + 判断分身）是场景三。与场景二的区别：场景二的知识服务一条具体协作流程（研发给产品经理看判断依据）；场景三的知识是老板的**整个判断体系**，主角是一把手，病症是组织级沟通成本。

### 设计原型

本场景的设计来自两次真实实践的合并：

- **过程原型**（教练如何跟老板工作）：多轮沟通 → 从会议转写中抽离老板发言（附说话人归属依据）→ 概念按"老板原话 / 顾问理解 / 员工语言"三栏拆解 → 陈述按"事实 / 意见 / 假设 / 决策候选"登记台账 → 已拍板内容形成编号决策记录（含重开条件）→ 理解校验清单区分"把握较高 / 待老板确认"。
- **结果原型**（成品长什么样）：方法论骨架页（填写表式，框架先于内容）、编号稳定决策、对话→可复用判断的转化样例（明确区分"稳定规则"与"不能跨项目复用的结论"）、知识边界声明（哪些内容不进库、为什么）。

结果原型的一个重要教训：只交付框架会得到"结构正确但内容空洞"的知识库——隐含判断藏在具体情境里，必须靠过程原型的情境深挖把内容挖出来。

## 访谈流程

场景三的核心是搞清楚**老板的词表、拍板方式和知识边界。**

访谈对象可能是老板本人，也可能是协助建库的人（顾问/助理/产品负责人）。访谈按以下顺序展开，每组问题问完后简要复述用户回答，确认理解再继续下一组。

### 第一步：问题定位（病症在哪）

提问：
1. 老板跟员工的沟通，最耗成本的是什么？
2. 哪些话需要反复解释？员工最常误解的是什么？
3. 老板不在场时，团队做判断的质量会掉多少？

访谈目的：确定知识库要解决的核心病症，直接决定重心——"听不懂"指向概念翻译层（concepts/），"判断依赖本人在场"指向决策规则层（decisions/ + cases/）。

追问方向：如果用户说"沟通挺好的"，问"最近一次员工把老板的意思理解偏了是什么时候"——具体事件比抽象评估可靠。

### 第二步：概念体系扫描（老板的词表）

提问：
1. 老板描述这门生意，会用哪些只有他自己（或少数人）懂的词？
2. 每个词精确的意思是什么？员工听到这个词时，以为它是什么意思？
3. 这些词之间是什么关系？

访谈目的：拿到概念种子。老板的抽象词汇是资产不是噪音，每个词都要进 `concepts/` 用三栏结构拆解。误解高发的词（员工以为 X、实际是 Y）优先级最高——它们就是沟通成本本身。

追问方向："能不能引用老板最近一次的原话来解释这个词？"原话是语义锚，Agent 后续所有理解都以它为准，防止漂移。

### 第三步：决策情境深挖（怎么拍板）

提问：
1. 老板最近一个重要决策是什么？当时的情境是什么？
2. 有哪些备选方案？每个方案为什么被排除？
3. 什么条件变了，老板会重开这个决定？
4. 老板事后复盘时说过"下次遇到类似情况要怎么判断"吗？

访谈目的：拿到决策案例种子。这是场景三最重要的访谈环节——直接问"决策标准是什么"只会得到空话，规则都藏在具体情境里。

每个案例必须挖出四个字段：**情境**（什么背景下做的决定）、**备选**（当时有哪些选项）、**排除理由**（为什么没选其他）、**反向条件**（什么条件出现时这个决定要重开）。四字段齐备且结果已知的案例才能支撑回放验证——用它测试 Agent 是否真学会了老板的判断。

追问方向：老板拿不出案例时，问"最近一次否决了下属的提案是什么时候"——否决理由是决策规则的富矿。

### 第四步：权威与边界（谁的话算数）

提问：
1. 团队里谁说的话老板认？谁的话算战略方向、谁的话算产品事实、谁的话只是执行现状？
2. 哪些内容不能进知识库？（未定的判断、敏感信息、仍在变的结论）
3. 员工转述老板的话时，怎么判断转述得对不对？

访谈目的：生成说话人权威表（写进 AGENTS.md）和知识边界（boundaries.md）。老板的个人纪律（如"只认事实、不认他人转述的意见"）要翻译成工程规则：主张必须挂说话人，员工意见不得冒充老板判断——这是防止知识库被污染的关键闸门。

### 第五步：内容种子（真实材料）

提问：
1. 有没有一段最近的会议转写、老板的语音口述、或他写的框架文档（Excel/Word）？
2. 没有的话，请老板现在口述五分钟：讲一遍最近给团队解释过的某个判断。

访谈目的：拿到真实原始材料，演示完整 Ingest 流程（发言抽离 → 概念拆解 → 主张登记 → 决策记录 → 理解校验，工作流定义见 templates.md 场景三 AGENTS.md 模板）。

## 边界情况处理

| 情况 | 处理方式 |
|------|---------|
| 用户说"把老板所有想法都放进去" | 用第一步的具体病症拉回来："先放员工误解最多的那个概念" |
| 访谈对象是助理而非老板本人 | 概念页"老板原话"栏标注为转述，进理解校验清单等老板确认 |
| 老板拿不出决策案例 | 改挖"最近一次否决下属提案"，否决理由是决策规则的富矿 |
| 老板用 Excel 框架思考 | Excel 的表头和分表结构就是概念体系骨架，优先拆解它 |
| 一场会冒出 10+ 个抽象概念 | 先建索引级概念页（只有原话+初步理解），标注"员工语言待补"，分批消化 |
| 老板既是知识源又亲自维护知识库 | 仍是场景三；AGENTS.md 中面向老板本人的查询模式优先 |
| 用户是老板本人且主要给自己用 | 无组织翻译需求则回退场景一；有员工受众才进场景三 |
| 老板的原话被员工大量转述 | 转述内容进 claims.md 并标注转述链，与原话分开，等待校验 |

## 翻译规则

### 访谈结果 → 目录结构

| 访谈维度 | 映射到目录 | 说明 |
|---------|-----------|------|
| 专属词表 | `wiki/concepts/` | 三栏概念页：老板原话 → Agent 理解 → 员工语言 |
| 决策案例种子 | `wiki/cases/` | 情境案例页，四字段强制（情境/备选/排除理由/反向条件） |
| 稳定下来的决策规则 | `wiki/decisions/` | 编号决策记录，含重开条件 |
| 方法论框架 | `wiki/methodology/` | 骨架页（填写表式），待填项显式标注 |
| 对话中产生的可复用判断 | `wiki/conversations/` | 对话→判断转化记录，区分"稳定规则"与"不能跨项目复用" |
| 说话人权威表 | `AGENTS.md` | 权威表作为 Ingest 的主张登记依据 |
| 知识边界 | `wiki/boundaries.md` | 哪些内容不进库、为什么 |
| 主张台账 | `wiki/claims.md` | 陈述按事实/意见/假设/决策候选登记，挂说话人 |
| 理解校验 | `wiki/verification.md` | 待确认项挂起，确认后升级 |
| 原始材料 | `raw/meetings/` `raw/dictations/` `raw/artifacts/` | 会议转写、口述记录、框架文档 |

场景三典型目录结构：

```
boss-brain/
├── AGENTS.md
├── README.md
├── .gitignore
├── raw/
│   ├── meetings/       # 会议转写
│   ├── dictations/     # 老板口述
│   └── artifacts/      # 老板的框架文档（Excel/Word 导出）
└── wiki/
    ├── index.md
    ├── log.md
    ├── concepts/       # 三栏概念页
    ├── methodology/    # 方法论骨架
    ├── decisions/      # 编号决策记录
    ├── cases/          # 情境案例（四字段）
    ├── conversations/  # 对话→判断转化
    ├── thoughts/       # 老板的反思（如有）
    ├── claims.md       # 主张台账
    ├── verification.md # 理解校验清单
    └── boundaries.md   # 知识边界
```

只创建用户会用到的目录。老板没有框架文档就不要建 `raw/artifacts/`；没有对话记录习惯就不建 `conversations/`。

## 访谈节奏提示

访谈对象如果是老板本人，注意这类沟通特征：信息密度大、抽象度高、容易一口气讲完整套体系。应对方式：

- 每听完一段长阐述，先复述结构（"您刚才讲了三层：A、B、C——我理解得对吗？"），确认后再追问细节
- 不要中途打断他的框架陈述去抠细节——先让框架讲完，框架本身就是概念体系的骨架
- 框架讲完立刻要原话锚点："这套说法您最近一次原样讲出来是什么时候？有转写或文档吗？"
- 理解校验当场生成：把握高的当场确认，拿不准的当场问，问不了的挂起进 verification.md
