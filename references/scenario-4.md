# 场景四：项目协作型知识库（过程可追溯的项目工作区）

## 场景定义

知识库存在的目的是**给在办项目建一个可追溯的工作区**：把会议记录、项目上下文统一归属，让没参加会议、不够了解项目的人，通过与 Agent 对话就能掌握当前进展和来龙去脉。

它补的是 SaaS 的空白：项目管理 / 客户管理 / 订单管理系统只记"结果状态"（任务已完成、订单已发货、客户已签约），不记"为什么变成这样"。场景四保存的是**过程**——谁在哪次会上说了什么、当时有哪些备选、为什么这么定、后来又改过什么。所以它的定位是**这些 SaaS 系统的补充，不是替代**。

同时它保存**确定性输出**：方案定稿、报价、合同、验收单。这类东西一旦定稿就是可存档的资产，不该跟会议纪要混在一起。

典型用户画像：同时推进多个在办项目的负责人或小团队。行业集中在售前、咨询、知识服务、定制交付——共同点是**以会议和沟通为主要工作形式，交付物是方案或服务而非代码，客户侧有多个角色参与决策**。

### 与前三场景的区别

| 维度 | 场景一 | 场景二 | 场景三 | 场景四 |
|---|---|---|---|---|
| 知识的主角 | 我 | 我 + 我的下游 | 老板 | **一件在办的事** |
| 知识性质 | 可复用的个人积累 | 可复用的规范方法 | 可复用的判断体系 | **不可复用、但这次必须记住的过程事实** |
| 组织方式 | 按知识类型 | 按协作流程 | 按判断体系 | **按项目 + 按时间** |
| 核心动作 | 摄入 → 沉淀 | 沉淀 → 编译成规则 | 抽取 → 校验 → 分身 | **归档 → 回写状态 → 可复述** |

最容易和场景二混淆。判据是一句话：

> **这条知识，明年做别的项目还用得上吗？**
> 用得上 → 场景二（进规范、方法论库）。
> 用不上，但这次项目必须记得 → 场景四（进项目工作区）。

场景四也不等于项目管理工具。它不维护任务列表、不排甘特图、不做工时统计。有人问"这个项目下一步做什么"，正确答案是"去项目管理系统看"；问"这个项目为什么走到这一步"，才是场景四。

### 设计原型

本场景的结构直接来自一套已验证的项目工作区模板，原样保留，不做裁剪：

- **五件套**：`00_项目元信息` / `01-项目上下文` / `02_沟通记录` / `03_方案对齐` / `04-解决方案输出`。五段按业务流程编号，不是按"输入输出"抽象分层。
- **过程与结果分离**：`02_沟通记录` 存过程（每次会议的原文 + 总结，同名成对）；`04-解决方案输出` 存确定性输出（定稿方案、报价、合同、验收单）。两者的区别是"可不可改"——过程记录只增不改，确定性输出定稿即归档。
- **项目上下文多源**：客户给的原始资料、我方主动调研、我方产品资料，都在 `01-项目上下文` 登记，用一张资料清单管住来源和状态。**客户提供不等于客户确认，原始资料不直接等于方案结论。**
- **状态页渐进拆分**：小项目用 `03_方案对齐.md` 单文件维护共识、决策、未决问题；出现三次以上重要沟通、多个并行工作流或明显权威冲突后，才拆成独立状态文件。

## 访谈流程

访谈的核心不是盘点，而是**带着一个正在推的项目，从它的起点走到现在**：客户最初给了什么、中间怎么沟通的、现在到哪了。只谈这一个项目，跑通全程，其他项目之后照着同样结构复制。

每一步用户回答后，Agent 必须给出**即时反馈**，不能只记录。反馈固定分三类：

- **归属**：这条信息该放哪（客户资料 / 我方调研 / 沟通记录 / 方案对齐 / 输出）
- **性质**：这条陈述是事实、客户观点、我方判断，还是已确认的决策
- **缺口**：这个项目的链路里还缺哪一段

反馈要短，一两句话，说完继续问。目的是让用户在建库之前就看到这套机制怎么工作。

### 第一步：锁定一个项目

提问：
1. 你现在手上正在推的那个项目是哪个？
2. 它从什么时候开始的？最开始是什么触发的——客户找过来、我们主动推、还是别人转介绍？
3. 现在推到哪一步了？

访谈目的：确定唯一的访谈对象。数量不是起点，具体这一个才是。

即时反馈：

- 用户一口气报了三个项目 → 选"本周真的在推"的那个，说明"先跑通这一个，剩下的按同样结构复制，不用一次建完"。
- 用户说不清现在到哪一步 → 这本身就是病症，记下来，第四步会用到。
- 用户说"就一个项目" → 更好，直接进第二步，不需要日后扩展。

### 第二步：项目的起点——客户给了什么

提问：
1. 这个项目最开始，客户给了你什么资料？品牌手册、产品数据、历史销售、竞品信息，还是什么都没有？
2. 除了客户给的，你自己做了什么调研？
3. 你们自己的产品资料放在哪？是独立管理的，还是散在各处？

访谈目的：确定 `01-项目上下文` 要建哪几层，以及这个项目有没有事实底座。

即时反馈（边听边给判断）：

- "品牌手册这类进 `01-客户原始资料`，原样保存，不改写"
- "客户口述的数据只能算 candidate-evidence，不能直接当方案结论"
- "你自己做的竞品分析进 `02-我方调研`，要标检索日期——竞品会变"
- "产品资料没有独立产品库的话，就要在 `01-项目上下文` 里加一层 `04-我方产品`"

缺口提示：如果用户说"资料都散在微信里""客户那边还没给"，直接指出——**这个项目目前没有可追溯的事实底座，方案里的判断会变成凭印象**。这正是要建 `01-项目上下文` 的理由。

### 第三步：过程——沟通记录长什么样

提问：
1. 这个项目到现在开过几次会？大概都是什么性质——对齐需求、评审方案、同步进度、还是随便聊聊？
2. 有转写吗？用什么工具？
3. 会后会整理纪要吗？整理完放在哪？
4. 有没有哪次会定了什么，后来又被推翻或改掉的？

访谈目的：确定 `02-沟通记录` 的实际形态，以及 Ingest 链路的起点。**场景四 90% 的内容来自会议**，如果用户完全没有转写习惯，要么先建立这个习惯，要么这个场景不适合他。

即时反馈（边听边给会议的"类型判断"）：

- **对齐型**：产生了共识 → 必须回写 `03_方案对齐` 的当前共识，并挂来源
- **评审型**：产生了决策 → 必须写成「问题 → 方案 → 依据」
- **同步型**：只更新进度 → 更新 `README` 的当前进展，不进共识表
- **探索型**：没有结论 → 原文留着就行，不必强行总结成纪要

缺口提示：第 4 问如果用户能举出例子，那个例子就是整个访谈里最有价值的种子——**要求他提供那次会议的原文**，第五步会用它演示。

### 第四步：当前状态——头尾对照

提问：
1. 这个项目现在最重要的三个判断是什么？分别是什么时候、在哪次会上定的？
2. 现在卡在哪？卡在谁那里？
3. 如果下周你休假，谁能接手？接手的人最可能问你什么？

访谈目的：拿到当前状态，并与第一步的起点做对照，找出链路断层。

即时反馈（直接指出断层，这比记录更重要）：

- "你说项目目标是 X，但它是在哪次会上定的？找不到来源——这条目前只能标 `proposed`，不能算 `confirmed`"
- "你说卡在预算，但资料和会议记录里看不到这个卡点是怎么形成的——缺一段过程"
- "这个判断是客户说的，还是你自己的判断？两者在库里要分开记"

缺口提示：这一步的收尾动作是**给用户一份缺口清单**——这个项目的链路目前缺哪几段（起点资料缺失 / 过程记录缺失 / 状态未编译 / 决策无来源）。这份清单就是接下来要补的料。

如果第 3 问答"没人能接手"，明确告诉他：**这就是建这个库的直接理由**，比任何方法论证都有说服力。

### 第五步：现场投喂一份真实材料

不要等库建完再放内容。访谈结束前就让用户给一份东西：

- 最近一次会议的转写（优先）
- 客户给的一份资料
- 或者他现在用来记进度的周报 / 备忘

拿到后现场跑一遍完整链路，每一步都说明"我在做什么、为什么"：

```
原文归位 → 写总结 → 回写 03_方案对齐 → 更新 README → 勾选「已回写」
```

**具体操作 Read `references/meeting-sop.md`**：7 步流程、9 条原则、总结结构模板、说话人映射的四个验证角度、会议类型与回写去向，都在那份文件里。本地录音可以先跑 `scripts/transcribe-media.py`，已有平台转写直接导出文本。

即时反馈：跑完给用户看**同一份材料的两种用法**：

- 归档前：只有当事人记得，问起来要靠回忆
- 归档后：新人问一句，就能拿到结论、来源、和当时为什么这么定

这一步是说服力的来源。用户看见机制运转过一次，后面才会自己往里投料。

## 边界情况处理

| 情况 | 处理方式 |
|------|---------|
| 用户一开口报了很多项目 | 只取"本周真的在推"的一个跑通全流程，其余说明"照着复制即可" |
| 在办项目超过 10 个 | 明确告知不适用：该用项目管理系统。可以只把最重要的 3-5 个搬进来 |
| 完全没有会议转写习惯 | 先建立"会后存原文"的习惯，否则场景四会退化成空壳；可从下一次会开始 |
| 用户手上只有结论没有过程 | 这正是他要建库的原因；先归档当前状态，标注 `compiled_through`，过程从下一次会开始积累 |
| 用户想要任务看板、甘特图 | 说明本场景不做这些，它是项目管理的补充，只记过程和为什么 |
| 项目信息高度敏感（客户保密要求） | 建议独立 git 仓库、单独控制访问；AGENTS.md 里写明哪些信息不得外传 |
| 一个项目持续几年，沟通记录几百场 | 按年份分子目录，或只保留近两年的详细记录，更早的只留总结 |
| 用户已经有完整项目管理系统 | 更好——场景四不复制任务数据，只补"为什么"这一层，通过链接指向系统 |
| 项目很短（一次交付就结束） | 仍适用，可以不要 `03_方案对齐.md`，共识直接写进 `README.md` |
| 产品资料已有独立产品库 | 不建 `04-我方产品/`，在资料清单里登记产品库位置即可 |
| 用户说"资料都在微信/客户手里" | 明确风险：没有事实底座，判断会变成凭印象；先建 `01-项目上下文` 并补资料清单 |

## 翻译规则

### 访谈结果 → 目录结构

| 访谈维度 | 映射到目录 | 说明 |
|---------|-----------|------|
| 试点项目 | `projects/<项目名>/` | 每个项目一个目录，独立完整 |
| 项目阶段与卡点 | `projects/<项目名>/README.md` | 项目驾驶舱：阶段、状态编译至、关键卡点、阅读入口 |
| 会议原文与总结 | `projects/<项目名>/02-沟通记录/` | 原文与总结同名成对，如 `0903-需求对齐-原文.md` / `0903-需求对齐-总结.md` |
| 客户资料 | `01-项目上下文/01-客户原始资料/` | 原样保存，不改写不覆盖 |
| 我方调研 | `01-项目上下文/02-我方调研/` | 动态事实标检索日期，使用前复核 |
| 资料解读 | `01-项目上下文/03-资料解读与映射/` | 写清"能支持什么、不能证明什么" |
| 我方产品资料 | `01-项目上下文/04-我方产品/` | 仅当产品资料没有独立产品库时创建 |
| 共识与决策 | `03_方案对齐.md` | 单文件起步；复杂后拆成 `03-方案对齐/` + `00_当前共识.md` |
| 确定性输出 | `04-解决方案输出/` | 定稿方案、报价、合同、验收单 |
| 项目元信息 | `00_项目元信息.md` | 客户方拍板人、决策链、干系人地图 |
| 全局项目总览 | `wiki/index.md`（库根） | 在办项目清单与各自阶段 |

### 访谈结果 → AGENTS.md 工作流

| 访谈维度 | 映射到工作流 |
|---------|------------|
| 会议转写工具 | Ingest 的起点：原文放哪、怎么命名（见 `references/meeting-sop.md`） |
| 纪要整理习惯与会议类型 | Ingest 的会议总结环节（按类型决定回写哪里，7 步流程见 meeting-sop） |
| 试点项目 | Query 的"切项目"约定：先确认问的是哪个项目 |
| 确定性输出 | 输出归档纪律：定稿即归档，旧版本不覆盖 |
| 项目敏感度 | 知识边界：哪些内容不得写进库 |
| 拍板人信息 | 归属纪律：每条结论必须挂说话人与场合 |
| 链路缺口 | AGENTS.md 的 Lint 检查项，建库后优先补 |

## 三条核心纪律

写进 AGENTS.md，不可省略。

### 纪律一：过程只增不改，结果定稿即归档

`02-沟通记录/` 里的原文和总结，写完就不再修改。发现记错了，追加一份更正记录，不覆盖原文件——因为过程记录的价值就在于它记录了"当时的理解"，改掉就失去了追溯性。

`04-解决方案输出/` 里的定稿文件同理：新版本另存，旧版本保留，文件名带日期。

### 纪律二：每次会议必须回写状态

会议总结写完后，必须更新对应项目的 `03_方案对齐.md`，并在 `README.md` 的变更日志里记一行。**不回写等于白整理**——下次有人问"现在什么情况"，Agent 还是会去翻纪要。

回写要标来源：每条结论挂上哪次会议、谁说的、什么时间。

### 纪律三：输出状态必须标日期

项目驾驶舱的 frontmatter 必须有 `compiled_through: YYYY-MM-DD`。回答"现在什么情况"时，若该日期距今超过两周，Agent 必须先声明："这份状态编译至 X 月 X 日，之后可能有新进展，需要我核对最近的会议记录吗？"

没有这一条，知识库会给出过时的确定答案，比不知道更危险。

## 访谈节奏提示

项目负责人的沟通特征是"结果导向"：他会直接讲"这个项目现在到哪一步了"，跳过过程。这时候要主动往回拉：

- 他说"已经跟客户对齐了"，追问"哪次会对齐的？会上定了什么、没定什么？"——**对齐的边界比对齐本身更重要**
- 他说"方案改过一次"，追问"为什么改？改之前是什么？"——改动的理由就是最有价值的因果信息
- 他说"这些都在我脑子里"，追问"如果下周你休假，谁能接手？"——接不了手，就是知识库存在的理由
- 他说"资料都在微信里"，追问"上次做方案，你翻了多少个地方找资料？"——翻的地方越多，越需要统一归属
